# Sinks

The runner reserves `.53` on the scan's subnet for DNS and `.9` for HTTP and TLS; read `Sandbox.dns_ip` and `Sandbox.http_ip` for the resolved addresses. `Sandbox.start_sinks()` starts both production sinks as hardened containers from `sink_image` (default `python:3.12-alpine`). The scripts are bind-mounted read-only, each sink appends to its own JSONL log file under a private `0700` per-scan directory, and the low ports come from the namespaced `net.ipv4.ip_unprivileged_port_start` sysctl, not a capability. The runner waits for each sink's `ready` record before continuing and fails closed with `SERVICE_START` when a sink dies or never reports.

The DNS sink answers every A query with the HTTP sink's address and logs each query, on UDP and TCP (`dig +tcp`-style exfil), decoding data hidden in labels as base32, base64, base64url or hex. The HTTP/TLS sink logs method, path, headers and body on `:80`, the TLS ClientHello SNI on `:443` without terminating TLS, and any TCP contact on `:80` that carries no parseable request — any contact is a hit. Each record carries the peer's source IP. When a sink's connection limit is reached it refuses further contacts, and each refusal is logged so a contact can never be dropped silently; the host treats a `refused` record as a log problem and fails the component with `SINK_LOG`.

`Sandbox.collect_sinks()` turns the logs into `dns_hits`, `http_hits` and `tls_hits`. A sink component is `complete` only when the sink reported ready, its container is still running at collection time, and its whole log parses with no problems and no truncation; anything else is `error` with `SINK_FAILED` or `SINK_LOG`. The TLS component shares the HTTP sink's container and log. Logs stop at a 4 MiB cap with a truncation marker, which also fails the component.

`Sandbox.start_service()` remains for trusted connectivity fixtures; it never marks a component complete. Never replace a sink container with a listener on the host.
