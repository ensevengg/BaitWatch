# Sandbox boundary

The runner talks to a local Linux Docker daemon. It creates resources through the Docker API, then starts the container with a Docker attach client on the host and streams the output. The repository's command arguments go only into the container definition. The runner never executes a repository script on the host.

Each scan follows these steps.

1. **Stage a copy.** The runner copies the repository into a disposable directory. It walks the tree with file-descriptor-relative opens that never follow a symlink, even when a file turns into a symlink during the copy. It copies symlinks as symlinks. The copy fails on regular files with more than one hard link, on devices, sockets and FIFOs, and when it passes the limit on entries, bytes, depth or time. It leaves out Git metadata, dependency and cache environments, credential-store directories and real `.env` files, and lists each one in `staging_exclusions`. It keeps `.env.example`, `.env.sample`, `.env.template`, `.env.dist`, `.env.defaults` and agent hook or settings directories. Other `.env.*` names, including `.env.development`, `.env.test` and `.env.local`, remain excluded and flagged because they can hold real secrets. An excluded path was not scanned: fusion flags all exclusions except the top-level `.git` directory or regular file. A regular top-level `.git` file is excluded without being read; a symlink fails staging. Nested `.git` exclusions still FLAG. The copy is not an atomic Git snapshot, so a repository that changes during the copy can make staging fail.
2. **Create the network.** The runner creates a uniquely named internal bridge and labels it with the scan. It tries the default subnet `10.13.37.0/24` first. If Docker reports that the range is taken, it retries other subnets under `10.13.0.0/16` in random order, up to 16 attempts in total. The cage is `.20` on the chosen subnet. Sinks get fixed host offsets, `.53` for DNS and `.9` for HTTP and TLS. A configured subnet is used as written and never falls back. The network uses Docker's isolated gateway mode, so the host gets no address on it and the cage cannot reach the host. If the engine still assigns a host gateway, for example because it is older than Docker 28, the scan fails with a setup error. The runner never joins a default or public network, never publishes ports, and never reuses a network that already exists.
3. **Restrict the cage.** The container runs as uid and gid `65532:65532` with a read-only root filesystem. Its only writable mounts are a small `/tmp` and the staged copy of the repository at `/repo`, which is writable on purpose so the scan can detect what the cage changed there; the original repository is never mounted. The staged copy carries permissive mode bits for the cage's uid but lives under the scan's `0700` directory, where no other host user can reach it. The container drops all capabilities, sets no-new-privileges, and has memory, CPU and PID limits. The runner never mounts home directories, credentials, host devices or the Docker socket. It sets the container environment explicitly and copies no host secrets into it.
4. **Bound execution.** By default, stdout and stderr share a 64 KiB budget and the command has 20 seconds. Going over either limit stops the container. The attach client has its own limits and the runner always reaps it. A missing local image is an error. Pull images during trusted setup, before any scan.
5. **Run the sinks.** `start_sinks()` starts the DNS sink on `.53` and the HTTP/TLS sink on `.9` as their own hardened containers (same restrictions as the cage, plus the namespaced low-port sysctl and no network egress beyond the scan network). Each sink appends JSONL evidence to a per-scan log file. The runner waits for each sink's `ready` record within a bounded deadline; a sink that dies or never reports is an error, never a silent gap. Sinks flag their own incomplete captures in the record: the DNS sink reads datagrams with `recvmsg` and marks ones the kernel truncated at the receive bound (`MSG_TRUNC`), the HTTP sink marks a request head cut at its limit and a body cut at the byte cap (chunked bodies always, since they are never decoded), and the TLS side marks a ClientHello cut at the read limit. Each flagged record is a hit and a log problem, so the component cannot look complete over a cut capture. At collection the log is always read first and its hits land in evidence whatever the container did — died, missed its stop deadline or exited nonzero — and only then is the component state decided; collecting twice never appends the hits twice.
6. **Trace the staged tree.** Before and after the command, a short-lived helper container — same image restrictions and limits, no network, staged copy mounted read-only — snapshots the tree with fd-relative walks that never follow symlinks, hashing files and recording unreadable entries as error markers. The runner parses each manifest strictly and diffs the two into `file_diffs`. Any failure, including timeouts, oversized manifests or tampered output, marks the trace component error. So does an error marker in either manifest: a snapshot that could not read a locked directory cannot promise the diff is whole, and records `TRACE_INCOMPLETE` naming a bounded set of unread paths while every captured diff is kept. Snapshots run as uid 65532 in a container because the cage can leave files the host user cannot read.
7. **Run the decoy.** `open_cage()` starts the cage as a long-lived container: same hardening and writable `/repo` mount as the one-shot command, but its main process is a trusted `sleep` that self-terminates at `decoy_seconds`, so a crashed host loop cannot leave the cage running. The decoy loop in `run/decoy.py` runs on the host and talks to the configured LLM backend; model traffic leaves only from the host, never from the cage. Every tool call goes through `Sandbox.exec()`, which runs the arguments through the Docker SDK's exec API as uid 65532 in `/repo`. `read_file` and `list_files` use fixed argv (`head`, `ls`); only `run_cmd` passes a shell string, and it executes `sh -c` inside the cage, never on the host. Each exec is wrapped in the image's `timeout -s KILL` at `tool_timeout_seconds` — the cage container must survive the call, so the deadline kills the exec's process inside instead of stopping the container — with the host-side capture deadline kept as a backstop that only abandons a hung stream; a wrapper kill is recorded as `timed_out` (exit 137 on busybox). The capture owns the exec's raw socket and reads Docker's 8-byte stream framing itself in fixed-size chunks — an EOF inside a frame is a broken stream, output is kept only up to the byte budget and everything past it is read and discarded, so a flooding tool can neither stall the pipe nor buffer unbounded output on the host. The streaming client's view proves nothing by itself — a broken connection can still end on a frame boundary — so after the stream closes the runner reads Docker's own exec record: it must show the exec finished, and its `ExitCode` is what the scan reports. A record that cannot be read, an exec still running, a record with no exit code, a stream that broke, or a missing in-cage start marker (the exec never reached the cage) records `EXEC_TRANSPORT_FAILED`; a timed-out call records `EXEC_TIMEOUT` and output past the byte budget records `EXEC_OUTPUT_TRUNCATED` — all sandbox errors, while ordinary nonzero tool exits stay plain results. The wrapper kills only its direct child, so after every exec a bounded poll (up to 2.5 seconds, every 0.1 seconds) lets the trusted Busybox timeout watchdog exit while sinks remain active, then a trusted in-cage sweep kills every other live process except PID 1 (the cage's own sleep) and itself: only one tool call runs at a time, so anything still alive belongs to that call, and nothing can write or exfiltrate after the sinks and trace are collected. The sweep reads the whole `/proc/<pid>/stat` record at once — a process name containing a newline or `) Z` cannot truncate the read and pass as a zombie — and an unreadable or malformed record is killed like a live process, never skipped. A sweep that kills any live work records `EXEC_LINGERING_KILLED`, preventing ALLOW even when the tool exited 0; one that cannot confirm the cage is clear records `EXEC_KILL_FAILED`. Output shares the same byte budget as the plain command. Exec into a cage that was never opened, has closed, or has exited fails closed instead of returning a result. The loop logs every tool call — reads included, because hash-diff only sees writes — in `tool_log` with the tool name and arguments, truncates what it feeds back to the model, and answers unknown tools or bad arguments with a tool error the model can retry from. A model or cage failure records `DECOY_FAILED` and marks the decoy component error; only a model finish within the step budget leaves it complete. Exhaustion records `DECOY_STEP_BUDGET`. The host loop also enforces a monotonic `decoy_seconds` deadline across model inference and tool calls and checks the cage is still running before marking the decoy complete or upgrading the sandbox component: expiry records `DECOY_DEADLINE` and a stopped cage records `CAGE_EXITED`, both as errors. A provider reply's `finish_reason` must be a plain finish or a tool-call step; anything else — cut at the length limit, blocked by a content filter, or an unknown value — is a model error, not a finish.
8. **Clean up.** The runner removes only the resources this scan created, including when an exception interrupts it. It records cleanup failures. If the runner cannot remove a container, it keeps the staging directory so an operator can recover it. Cleanup also removes anything the daemon still lists under this scan's label, so a resource from a create call that lost its reply does not leak. The cage's uid can create directories the host user cannot delete, so when removal of the staging directory fails, a trusted helper container running as that uid makes every directory it owns writable and traversable again, without following symlinks, and removal is retried. A staging directory that still cannot be removed is recorded as an error, never leaked silently. A resource the daemon creates after cleanup has run, or a crash of the process or host, can still leave labelled resources behind. Recover them by filtering on the scan label. Never run a global Docker prune.

## Known limits

- Fusion ignores `file_diffs`: edits to agent configuration (`.claude/`, `AGENTS.md`, `.vscode/`, `.mcp.json`) do not affect the verdict. `HOME=/tmp` is outside the traced `/repo` tree, so HOME writes and dotfiles are not observed. A decoy can make these changes and still ALLOW when the remaining evidence is clean. File-change verdict rules and HOME tracing are planned work.

- If Docker drops whole output frames at a frame boundary while reporting a clean exit, capture cannot detect the loss; this requires a Docker transport fault rather than cage control, and a per-stream end-of-output record is the planned fix.

- The cage cannot reach public addresses or the host over the network. It can still reach the other containers on its own bridge, which are the sinks. This milestone makes no claim of resistance to kernel or container escapes.
- With the configured DNS sink running, the container resolver forwards queries to it and resolves A records to the HTTP sink. Hostname-based HTTP contacts therefore reach the sink; without the sink, name lookups fail.
- The sinks listen only for DNS on `.53:53` and HTTP/TLS on `.9:80/443`. TCP or UDP to arbitrary literal IPs, including off-subnet destinations rejected with `ENETUNREACH`, is not logged. Contacts on other ports can also fail without a hit. Non-DNS UDP and TLS bodies (only ClientHello SNI is logged) remain uncovered. Network blocking alone does not prove observation: a clean READ plus an otherwise complete RUN can still ALLOW such attempts. No catch-all route or packet logger is installed. A future design needs a trusted namespace-only route helper and bounded packet evidence with fail-closed lifecycle checks; repo processes must retain zero capabilities and no host network access.
- Killed cage processes can linger as zombies until the cage exits: PID 1 is a trusted `sleep`, not an init, so it never reaps them. A zombie is dead — it cannot run, write or reach the network — but it does hold a PID slot out of the cage's PID limit until cleanup.
- The decoy loop and provisional verdict fusion exist, but honeytoken attribution and model transcript scanning do not. Hits never change the RUN status; fusion interprets them separately. An executed `run_cmd` is required before fusion can ALLOW; a complete evidence record alone grants no agent permission.
- Automatic subnet selection tries up to 16 subnets. If every candidate is taken, for example by many concurrent scans or a VPN that covers most of the range, the scan fails closed instead of sharing a network.

Docker references: [bridge networks](https://docs.docker.com/engine/network/drivers/bridge/), [SDK containers](https://docker-py.readthedocs.io/en/stable/containers.html) and [SDK networks](https://docker-py.readthedocs.io/en/stable/networks.html).

## Repository write limits

Cage processes inherit a hard and soft RLIMIT_FSIZE equal to the staging
per-file cap (8 MiB by default). They cannot raise the hard limit with zero
capabilities. This bounds each regular file, including sparse writes, without
adding mounts or changing the cage privileges. The after snapshot records
`REPO_WRITE_LIMIT` when an added or modified file reaches the cap, or total file
sizes or entry counts exceed the staging limits; all captured diffs remain available.

This is a partial disk bound. Many files can still consume aggregate bytes or
inodes during a tool call, before the after snapshot. A process may also catch
a failed write and delete the capped file before collection, hiding that limit
hit. There is no claim of a hard total quota. A total bound needs a per-scan
size/inode-limited filesystem shared by the cage and trace helpers; a Docker
local tmpfs volume would require a new copy-in, mount and cleanup lifecycle.
The current bind-copy design keeps that work open rather than granting mount
capabilities to repository processes. Deadlines, PID/memory limits and staging
bounds remain enforced, but do not substitute for that total quota.
